The complexity

This is not a to-do app

Speed means little if the thing is simple. HomeNetWatch spans hardware, kernel networking, cryptography, internet routing data, a time-series store and a real-time interface.

A distributed system

Four runtimes talking to each other: a Python agent on a Pi, a FastAPI server, a Postgres database and a React single-page app, plus a WireGuard hub, a traffic generator and a Kismet survey radio.

Security as a feature

Signed enrollment, a pinned TLS key, admin approval, per-device WireGuard tunnels, roles enforced on the server, CSRF, HSTS and an enforced CSP. The guest role is read-only and hides my public IP.

Kernel-level networking

Wired and Wi-Fi measured separately on one machine. Sockets are steered per interface in a small C shim, and flows share a container network namespace with the VPN.

Internet-routing intelligence

Traceroutes enriched with ASN, IXP and RPKI data, grouped by owning network, and compared with the path BGP announces.

Data with a lifecycle

24 tables and 34 migrations. Raw results for six months, rolled up to hourly and daily averages so history stays cheap.

A real-time interface

Animated React Flow diagrams, drag-to-zoom charts, a layout that works on a phone, and on-demand traces that round-trip through the Pi in seconds.

Challenges and limitations

Real projects run on real budgets. These constraints shaped the design, and working inside them is part of the skill.

AI coding is not cheap

Heavy AI-assisted development adds up quickly. I spread the work across several coding agents and used the Git repository as the coordination layer: one source of truth, a branch per task, pull requests as the hand-off, and written rules that every agent follows.

Home hardware is not enterprise grade

A home router and a Raspberry Pi have little CPU, memory and bandwidth to spare, and few options to tune. I worked within that by controlling how resources are used: checks are scheduled and spaced out, heavy tests never overlap, and only one on-demand trace runs at a time.

Cloud resources are expensive

I know AWS and GCP well, but my goal was to keep the cost as low as possible, ideally free. So I moved to Oracle Cloud and its free tier, and designed the server to be small: thin APIs, rolled-up history and a demo that cannot start expensive work.

Testing without a fleet of devices

A separate non-production environment is a must for safe testing. That would mean a separate physical Raspberry Pi for each environment, and I did not want to buy more hardware until I could prove that one would work for this project. It has, so that is now an easier decision. Until then, virtual Pi instances stand in for most of it. They work, with limits: they cannot reproduce real Wi-Fi radios or the behaviour of a real home network.

Phase 2.0: an agentic operations AI, not yet

The next step I would love to build is a set of agentic AIs that automate log analysis, identify the root cause of an outage, and then act: restore service, fix the issue, and even contact the ISP to get service back. It is a plan, not a build. Running agents like that costs real money, which makes it impractical for now. It stays on the roadmap as Phase 2.0, for when the economics catch up.
