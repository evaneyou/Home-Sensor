Find out exactly where your internet breaks, and prove it.

HomeNetWatch is a network observability platform I designed, built, secured and run in production. A Raspberry Pi inside the home tests the wired and Wi-Fi paths around the clock. A server turns the results into a plain answer: what is healthy, what is degraded, and at which hop a problem starts.

The project

A network tool that explains itself

Most speed tests give a number. HomeNetWatch gives a diagnosis: which network, which hop, which stage of the connection, and whether it is the wire or the Wi-Fi.

Staged tests

Every web check is broken into DNS, TCP, TLS and time to first byte, so a failure points at its cause. Ping, MTR path traces and a bandwidth test round it out.

Wired against Wi-Fi

The Pi has two uplinks and measures each one separately. Every test is pinned to its own interface, so the comparison is honest.

Path View

A traceroute rebuilt for people: hops grouped by the network that owns them, latency added at each handoff, IXPs recognised, and the observed path checked against what BGP announces, with RPKI.

Network Path Diagram

An animated React Flow diagram of the route each test takes. Signalling rides the WireGuard tunnel; payload goes direct to the internet. Hover any box for details.

Airwaves

A second radio runs Kismet to survey the neighbourhood: nearby networks, channels and clients, with trusted access points flagged.

Trace anything, on demand

Type a host or public IP into Path View and the Pi traces it over the link you choose, then draws the result in the same diagram.

Architecture

Designed so the home stays closed

The Pi only ever makes outbound connections, and the dashboard never talks to it. Everything between them is authenticated, and every permission is enforced on the server.

Read the full spec (SPEC.md)
  • Signed enrollment. A new Pi checks in with a signed request, pins the server's TLS key and waits for my approval before it receives a WireGuard tunnel.
  • Roles on the server. Admin, read-only viewer and a guest role. The UI hides things as a courtesy; the API is what refuses them.
  • Thin APIs, honest data. Raw results are kept for six months, then rolled up to hourly and daily averages, so history stays cheap.
  • Hardened edge. Automatic HTTPS, HSTS, an enforced Content-Security-Policy, a Permissions-Policy, CSRF protection and CI on every change.

Problem solving

Four problems that were not in the tutorial

A measurement that quietly lied

Every measurement flow was leaving by the default route, so the wired and Wi-Fi results looked the same. A small C LD_PRELOAD shim was meant to pin each socket to one interface, but the sender had already bound its port, so the shim's own bind always failed. I found the cause, steered the socket with IP_UNICAST_IF instead, which works after a bind and needs no privilege, and confirmed in the data that the Wi-Fi uplink finally behaved like Wi-Fi.

A container that said "Up" and did nothing

The flow generator shares the VPN container's network namespace. Rebuilding the VPN left it running with no listener, so every flow failed while every status stayed green. I traced it from the symptom, added a deploy script that recreates the two together, logged the failure loudly, and wrote it into the runbook.

Reading a traceroute like a person

Raw hops are IP addresses and silence. I enrich them with ASN, IXP and RPKI data, group them by owner, and handle the awkward cases: an interconnect address that belongs to the neighbour, and routers that never answer, which are shown as a gap rather than a fault.

A public demo on a private network

Showing real data to strangers means designing for them. The guest role is read-only on the server, has no access to my public IP, expires when idle, and every visit is recorded for me to review.

Leadership and process

Run like a team project, even as a team of one

I treat the repository as a product other people could join tomorrow. The rules are written down, and the tooling enforces them.

Spec first

One document owns the architecture, API and phase plan, with an explicit list of what is out of scope.

Every change reviewed

Feature branches, pull requests, CI for server tests, the dashboard build and the Compose config, and conventional commits.

Safe to ship

Database migrations, backups before risky deploys, semantic versions and a changelog written for readers.

Open by default

Contributing guide, code of conduct, security policy, MIT licence, and a deployment guide that starts from a blank server.

I also build with an AI coding assistant. I set the direction, write the rules it works under, review what it produces and decide what ships, and the pull-request history shows exactly that division of labour.
